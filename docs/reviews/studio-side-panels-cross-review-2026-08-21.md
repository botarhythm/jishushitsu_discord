## 第1ターン: 両者一致の Critical

**パネル開閉がクロップ対象（収録ステージ）をリサイズし、録画途中で解像度が変わる。**

- Region Capture は最初の矩形を固定する API ではなく、対象要素の bounding box に毎フレーム追従する
- Chromium の MediaRecorder は新しいフレーム寸法を検出するとエンコーダを再生成する一方、WebM muxer のトラック寸法は最初の映像フレームで一度だけ初期化される
- 結果、トラック宣言寸法と後続フレームが食い違う WebM が生成され得る
- これは c709e0f で直した「尺・索引の欠落」とは別경路の破損で、ts-ebml による Duration/Cues 注入では直らない
- W3C 仕様・MDN はリサイズ時のフレーム寸法挙動を明文化していない（実装依存）ことを当方でも確認済み

**副産物（重大）**: 既存のチャットパネルも同じ flex 兄弟方式のため、**録画中にチャットを開閉すると同じ破損が起きる既存の本番バグ**である。両系統が独立に指摘。

## 第2ターン: 3案の裁定

| 案 | 内容 | 裁定 |
|---|---|---|
| A | 録画中は列を常時予約 | 両者却下（毎回の収録画質を恒久的に犠牲にする） |
| B | 固定サイズ canvas 経由で録画 | 両者却下（非アクティブ時に rAF/rVFC が停止し映像だけ凍結→A/V不整合。既往の音声負荷問題にも触れる） |
| **C** | Document Picture-in-Picture でタブ外へ出す | **両者採用** |

**Codex の重要な補足**: 案C 単独では解像度固定を保証しない。既存チャット、ブラウザウィンドウのリサイズ、OS 表示倍率変更でも同じことが起きる。Document PiP は **1タブにつき1ウィンドウ**のため、AI設定とチャットを別々には出せない。

## 当方の追加調査（両レビュアーの見落とし）

実機の Chrome 148 に **`RestrictionTarget`（Element Capture API）が存在する**ことを確認した。

- Element Capture は対象要素の**サブツリーのみ**を捕捉し、**視覚的に重なる要素を除外する**（Region Capture は矩形を覆うピクセルをそのまま録る）
- したがってパネルを `position: fixed` のオーバーレイに戻せば、**レイアウトを一切動かさずに**（＝解像度を変えずに）録画から除外できる
- 要件: 対象要素が独自のスタッキングコンテキストを形成すること（`isolation: isolate`）
- 注意: 対象が要件を満たさなくなると**新しいフレームが出力されなくなる**（映像が凍結する）

案C（DocPiP）より単純かつ本件に適合する可能性が高く、次フェーズで検証する。

## 今回入れた暫定措置（本コミット）

恒久対策までの間、本番を安全側に倒す。

1. 録画中および**録画開始処理中**は、チャット・AI設定の**両方**の開閉を封鎖（UI の disabled とハンドラの二重防御）
2. 録画開始時にパネルが開いていたら、**その操作では録画を開始せず**閉じるに留め、再操作を促す
3. `cropTarget` を要求したのに確保できない場合は**録画を中止**する（タブ全体録画への黙示フォールバックを廃止）
4. パネル内の「AI参加者を無効にする」を録画中 disabled に
5. 内向きの影を削除、`aria-labelledby` を付与
6. `ResizeObserver` で録画中のステージ伸縮を検知し、ユーザーに見える警告を出す（最後の防波堤）

## 恒久対策の残タスク（実装GOの必須条件）

1. パネルをタブのレイアウトから外す（Element Capture 併用のオーバーレイ、または Document PiP 講師コンソール）
2. 既存チャットの開閉によるステージリサイズも同時に除去する
3. Chrome / Edge の対象バージョンを定め、**PiP/オーバーレイ内の UI が録画へ一切映らないことを実映像で確認**する
4. パネル開閉・チャット開閉・ウィンドウリサイズ・AI 配線変更を含む実機収録を行う
5. 出力 WebM について Duration/Cues、全フレームデコード、Canva 取込、MP4 書出しまで確認する

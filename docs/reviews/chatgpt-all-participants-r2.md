## F-2-01 予約AI接続への移行後の返答音声の重複排除が未定義
- severity: P2
- affected: FR-002 / FR-004 / FR-011 / RAC-007
- evidence: FR-002はAI音声を別の予約participant接続からpublishする。`components/RoomView.tsx:121`には`RoomAudioRenderer`があり、`hooks/useAiParticipant.ts:135`～145にはホスト向け直接モニタ再生がある。`components/RoomView.tsx:306`～310はregistryとタブ音声の重複防止を扱う。FR-011が明記する重複防止はタブ音声についてのみ。
- failure scenario: publish先だけを予約AI接続へ変更して直接モニタを保持すると、人間として接続している操作講師には予約participantの返答と直接モニタの返答が両方届き得る。単一publishと「全員が聞こえる」を満たしても、講師には遅延した二重音声になる。
- gap: missing — 返答のpublish本数とは別に、操作講師を含む各受信者の再生経路数が規定されていない。録画についても予約AI受信と既存registryの選択方針が未定義。
- proposed resolution: FR-011に、各人の返答再生と各録画へのAI音声取り込みをそれぞれ一経路に限定することを追加する。操作講師の直接モニタ・予約participant受信・外部モニタ設定の優先関係を設計で定める。
- proposed test: 操作講師と受講生がいるルームで識別可能なAIテスト音声をpublishし、操作講師のモニタ設定を切り替え、通常／収録モードと録画を確認する → 各人の再生と各録画にAI音声が一回だけ現れ、停止・再publishでも重複しない。

## F-2-02 一括修復の途中失敗時の契約が不足
- severity: P2
- affected: FR-007 / FR-008 / RAC-005
- evidence: FR-008は事前の曖昧・欠落を「変更せず失敗」とする一方、書き込み途中の失敗を規定していない。`scripts/check-chatgpt-audio.ps1`の`if ($Fix)`ブロックはIN1割当、A1/B1、mute、Virtual Input、再起動を順次実行している。`components/AiParticipantSetupModal.tsx:497`～510も設定patchと通話マイク変更を別々に開始している。
- failure scenario: 一意なデバイス解決後、VoiceMeeterの変更には成功するが既定通信入力の変更が失敗する。またはブラウザ設定の保存後、通話マイク切替が失敗する。設定は混在状態になり、再実行時に利用者がどの変更まで成立したか判断できない。
- gap: missing — 途中失敗、実値の再取得失敗、復旧の再実行に対する結果と回復方法がない。成功時と事前検証失敗だけを検証する実装でRAC-005を満たせる。
- proposed resolution: 各操作の適用前値・要求値・適用後実値と成功／失敗／未確認を返すこと、部分成功では完了や検証済みとしないこと、残存変更と次の操作を示すことを追加する。安全に実行できる範囲での復元または部分適用の維持を明示し、同じ要求の再実行を許容する。
- proposed test: 各書き込み段階と実値取得に障害を注入し、その後同じ修復要求を再実行する → 部分適用を正しく表示し、スクリプトは非ゼロ終了、検証記録は成立せず、再実行によって要求値へ収束する。

## F-2-03 ルーム移動と接続復旧後の再開方針が曖昧
- severity: P2
- affected: FR-002 / FR-003 / FR-010 / FR-012 / RAC-004
- evidence: Scopeは「現在ルームに追従」、FR-003は「ルーム移動に追従」とする。一方、FR-010はルーム移動・LiveKit切断で停止して「遅延処理で再publishしない」とし、FR-012は「再取得は明示操作に限る」とする。RAC-004は移動・再接続を試験対象にするが、復旧後の期待状態は単一稼働以外に規定していない。
- failure scenario: AI有効中に講師がルームAからBへ移動する。実装AはAの処理を破棄してBで新たに自動開始し、実装Bは停止状態で参加操作を待つ。双方が「追従」と「古い遅延処理の禁止」を異なる解釈で満たせる。ネットワーク復旧後についても同じ分岐が生じる。
- gap: ambiguous — 停止と再開の状態遷移、および「明示操作に限る」の適用範囲が未確定。
- proposed resolution: 少なくとも明示停止、ルーム移動、一般の接続切断、予約identity置換について、AI有効状態を保持するか、復旧後に自動接続するか、参加の再操作が必要かを表で定義する。古い処理の無効化と新しい接続開始を区別する。
- proposed test: AI稼働中に各イベントを起こし、接続とデバイス取得の完了順を入れ替える → 旧ルームには再publishせず、新ルーム／復旧後は定義した自動再開または明示再開だけが成立する。

## F-2-04 初回の往復確認を行うための未検証接続は許可されるか
- severity: question
- affected: FR-006 / FR-007 / RAC-002 / RAC-006
- evidence: FR-006は未検証状態を設定パネルへ誘導し、RAC-006は実機のリモート音声による往復確認を要求する。既存の`components/AiParticipantSetupModal.tsx:513`～527は未検証でも有効化でき、検証記録の保存とは分けている。
- failure scenario: 初回セットアップで往復確認記録がない。接続条件を全面的に検証記録へ統一すると確認用音声を流せない。一方、設定パネルの既存有効化を無制限に残すと、通常参加との区別が実装者任せになる。
- gap: ambiguous — 初回確認用接続の許可条件、状態表示、終了条件が明示されていない。現時点では必ず行き詰まるとは断定しない。
- proposed resolution: 設定パネルから明示操作で未検証の確認用接続を開始できるかを決定し、許可する場合は通常参加と同じ権限・単一接続・停止処理を適用する。確認前は未検証と表示し、RAC-006合格後だけ往復確認を保存する。
- proposed test: 保存データがない状態から初回設定を通して実機往復確認まで実行する → 記録を事前作成せず到達でき、未合格時には検証記録が保存されない。

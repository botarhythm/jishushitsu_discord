# 会話音声のランダムな遅延：調査結果

- 調査日: 2026-09-23 JST
- 対象コミット: `5395cbe`（調査時の main）
- 利用者報告: 昨晩のZoom収録では問題なし。自習室は「会話の声が遅れて届く」。遅れ方はランダムな印象。
- 範囲: コード、導入済みSDK、デプロイ履歴、現在の音声設定の読み取り、独立したChromiumでのWebRTC実験。製品コード・Windows設定・本番設定の変更なし。

## 結論

自習室側に調査・改善すべき実装上の問題がある。ただし、昨夜の通話音声の遅延原因を特定したとはいえない。
追加情報により、Zoomと自習室はこのPC・同じ回線を使った比較と確認できた。アプリ間では音声デバイス選択、メディア中継経路、ブラウザとネイティブの処理、録画方法が異なるため、その差は残る。参加者・選択デバイスの完全一致は未確認。

## 追加情報による絞り込み

利用者からの追加報告:

1. 同じPC・同じ回線を使用。
2. ChatGPTを参加させたPCで録画すると顕著に動作遅延が生じ、デバッグした。
3. ChatGPTを起動して、セッション先のPCでは保存できた。保存成功と、遅延が皆無だったことは区別する。
4. Zoomに参加し、セッション先のPCで保存した場合は大変スムーズ。
5. その後、自習室で計4名のセッション。録画なしでも利用者のPCだけに遅延が生じた。
6. 4名セッションは最初ChatGPTを動かし、途中でChatGPT本体と自習室内のAI参加を両方停止した。停止後もランダムに遅延が発生し、利用者だけ一時的に会話から取り残されるような状態が複数回あった。
7. 遅延の方向は「両方、または判断できない」。受信だけ・送信だけとはまだ分類できない。

このため「録画エンコーダー単独が主因」という仮説の優先度を下げる。録画は悪化要因である可能性が残るが、録画なしの再現を説明する必要がある。同じ回線のZoomが正常で、自習室はこのPCだけに症状が出るため、このPCの自習室クライアントと音声デバイス・ブラウザ実行環境・個別のLiveKit接続経路の組合せを優先する。回線全般の不良や全参加者共通のサーバー遅延とは決めつけない。

### ChatGPT本体の停止と、自習室のAI処理の停止は別

`lib/ai/desktop-chatgpt-provider.ts` はChatGPTプロセスを監視せず、VB-CABLEを `getUserMedia` で開く。停止を検知するのはデバイストラックの終了であり、ChatGPT音声会話の終了ではない。
`hooks/useAiParticipant.ts:326-344` の人間音声ミキサーはAI有効状態と接続状態で動作する。自習室のAI参加が有効で仮想デバイスが生きていれば、ChatGPT本体が無音でも入力合成・追加のLiveKit接続・音声解析が継続し得る。
`components/ParticipantGrid.tsx:49` は通常モードにもAI球を描画する。`components/AiEnergyOrb.tsx:163` の描画ループは無発話時も継続するため、録画を止めただけではこの描画負荷は消えない。

これは一般的な外部音声連携の動作の説明に留める。追加確認により今回は自習室内のAI参加も停止済みであり、「ChatGPT本体だけを止めてAI参加を残していた」という仮説は除外する。停止処理の不備の有無は別途コードと実行状態で判断する。

### AI参加停止後にも発生した一時的な会話からの脱落

一定のバッファ時間だけでなく、一時的な通信・送受信処理・再生の停止として調べる必要がある。聞こえなかった部分が後から流れたのか、欠落して現在の会話へ戻ったのかはまだ区別できていない。

追加コード確認:

- AI参加を無効にした場合、`useAiParticipant` は入力ミキサーの停止、Providerの取り込みトラック停止、AI用Room切断を実行する。`ChatGptInputMixer.stop()` は音声ノードと再生要素を除去し、定期マイク確認も解除する。停止後にAI処理が必ず残るという実装ではない。ネットワークを伴う非同期処理の実際の完了時刻は未測定。
- 通話Roomの再接続はSDK任せ。アプリにはAI参加と独立した `Reconnecting` / `Reconnected` / `ConnectionStateChanged` の時系列診断や、再接続中の明確な通知がない。`StartAudioBanner` は自動再生許可の問題に対応するもので、通信停滞を表すものではない。
- 講師ダッシュボードの通信品質表示は `connectionQuality` による緑/黄の点だけ。音声が何秒止まったか、回復したか、どの段階で滞ったかは分からない。
- 導入済みSDKの `DefaultReconnectPolicy` には0ms、300ms、以降1.2秒・2.7秒・4.8秒・7秒にランダム加算する再試行間隔がある。これは切断時に作動する通常の再接続方針であり、接続中の音声にその秒数を足すコードではない。「ランダム」との表現だけで再接続が発生した証拠にはしない。
- `useLiveKitRoom` はoptionsをJSON文字列で比較してRoomを生成するため、`RoomView` のoptionsオブジェクトがインラインであることだけで、毎描画時に再接続するわけではない。

優先して検証するのは、このPCの①通信断/ICE復旧、②受信バッファ増大/パケット損失、③ブラウザや音声デバイスの一時停止。受信だけか送信にも影響したかが未確定なので、送受信双方と相手側の状態を記録する必要がある。現時点で三者のどれかに原因を確定する証拠はない。録画・AIを動かしたままだったという説明を原因に据えない。

### 再確認した録画処理の範囲

- `useLocalRecording` の重い処理は `start` の内部にあり、フックが存在するだけで動画エンコードが常時始まるわけではない。
- 正常停止経路にはキャプチャトラック停止、音声ノード切断、録画用AudioContext終了がある。
- 一方、ルーム移動は `RoomView.tsx:115` のkey変更による再マウントを伴う。`changeRoom` は録画停止を待たず、録画フック自身にもアンマウント時の停止処理がない。録画中にルームを移動した場合に旧録画資源が残り得る実装上の穴がある。ただし昨夜その操作をした証拠はなく、今回の原因とは扱わない。
- 保存時の `lib/webm-seek-metadata.ts:40-42` は録画全体をArrayBufferに読み、同期的に解析する。保存直後の操作停止の候補だが、未録画の4名通話全体の遅延をこれだけで説明はできない。

次の再現確認は、録画オフに加えて自習室内のAI参加オフを明確にした通話から始める。既存処理の残留を区別するには、新規入室時と同じタブで録画・AIを停止した後も比較する。音声のみ→映像追加→AI参加追加→録画追加の各状態で送受信双方の数値を採り、遅延の出る段階を特定する。

## 確認済みの問題

### 1. 通話音声の遅延を測定・保存していない

`lib/studio-video-playout.ts:14,58` は映像だけを対象にし、5秒ごとの取得値も閾値を超えた場合にconsoleへ出すだけ。
`lib/recording-health.ts:44-59` は録画用AudioContextのクロックと実時間の差を測る。
`hooks/useLocalRecording.ts:824-827` は停止時に録画健全性をconsoleへ出力する。

これらでは通話音声の受信バッファ時間、パケット損失、音声補間、ICE選択経路、RTT、送信側の負荷を時系列で照合できない。録画用クロックの遅れは、人間同士の通話遅延の測定値ではない。
また、クロック差だけで表示する「PCの処理が追いつかない」という説明は原因を絞りすぎている。CPU使用率や処理停止の原因そのものは計測していない。

現在のローカル設定にあるLiveKit Cloudへの読み取り専用 `listRooms` は活動中ルーム0件だった。昨夜の通話の受信統計は今回取得できていない。ローカル設定と本番環境変数の一致も、この確認だけでは証明できない。

### 2. 「低遅延化」の100ms指定は、状況によって待ち時間を増やす

`lib/studio-video-playout.ts:4,20` は `jitterBufferTarget=100` を全リモート映像に設定する。これは最大遅延100msの保証ではない。
映像と音声が同期される場合、仕様上は双方に大きい方のtargetを使うことが推奨される。そのため、コメントの「without changing audio」を無条件には保証できない。

独立したChromium 151.0.7922.34で、合成音声と320×180/30fpsのCanvas映像をローカルのRTCPeerConnection間で送信した。物理マイク、カメラ、実通話、本番LiveKit接続は使わず、音量0で再生した。設定ごとに新規接続し、2.5秒後から4秒間の統計差分を取得。順序は未指定→100ms→未指定→100ms。

| 設定 | 音声バッファ平均 ms | 映像バッファ平均 ms | パケット損失 |
|---|---:|---:|---:|
| 未指定・1回目 | 32.50 | 8.47 | 0 |
| 映像100ms・1回目 | 33.73 | 83.03 | 0 |
| 未指定・2回目 | 33.58 | 8.39 | 0 |
| 映像100ms・2回目 | 33.75 | 82.58 | 0 |

算出方法: `1000 * ΔjitterBufferDelay / ΔjitterBufferEmittedCount`。これは受信バッファの滞在時間であり、口元から耳までの遅延ではない。

この実験では映像の待ち時間増加を確認したが、音声の大きな遅延は再現しなかった。したがって今回の声の遅延の主因とは断定しない。実際のLiveKitの同期条件や混雑回線では結果が異なり得る。

デプロイ履歴上、この指定の追加 `3714e58` は9/22 20:11:39 JSTに成功。VP9強制と不要なタブ音声取得の削減 `4ab08e2` は同日22:09:40 JSTに成功。昨夜どのビルドのタブで収録したかは未確認。デプロイ成功だけでは開きっぱなしのタブへの反映を保証しない。

### 3. 既定の仮想マイクで入室する経路にガードがない

読み取り専用 `scripts/check-chatgpt-audio.ps1` の現在値:

- 再生既定・既定通信: スピーカー（Realtek）
- 録音既定: CABLE Output（VB-Audio Virtual Cable）
- 録音既定通信: Voicemeeter Out B1
- VoiceMeeter IN1: 物理マイク配列、A1=0、B1=1
- VoiceMeeter Virtual Input: A1=0、B1=1

`components/PreJoinScreen.tsx` はマイクのON/OFFだけを選択し、`components/RoomView.tsx:119` は `audio={initialMicOn}` で入室する。導入済みSDKの `audioDefaults` は `deviceId: { ideal: 'default' }`。この経路は物理マイクを保証しない。

AI起動時の推奨適用では物理マイクへ切り替える処理があるが、入室時から適用されるわけではなく、録画中は切替を避ける。ブラウザ側の既定選択や実際のtrack settingsを確認する必要がある。
Zoomが別のマイクを選んでいた場合、同じPCでも異なる入力経路になる。これは誤入力・音の回り込みのリスクであり、それだけでランダムな声の遅れを説明したとはいえない。
診断時に発話を依頼していないため、短時間のB1低レベルは異常の証拠として扱わない。

## 遅延候補と、まだ分かっていないこと

- 人間音声は `CallAudioRenderer` → SDK `AudioTrack` → HTML audioで直接再生する。ChatGPT入力用の `latencyHint: 'playback'` のAudioContextを直列には通らない。ここだけを変更して人間同士の遅延が直るとはいえない。
- 人間の送信は96kbpsの音楽用設定、DTXなし、REDあり。SDK既定の48kbpsより設定上の音声ビットレート上限は高い。ただし実際の使用帯域・回線の混雑は不明で、高音質設定だけを原因とは扱わない。SDK側で音声の送信priorityは既にhigh。
- 収録時は受信・描画に加えて自タブキャプチャ、音声ミックス、動画再エンコード、チャンク保持・IndexedDB保存を同じブラウザで行う。AI球は全ステージのCanvasを毎描画フレーム更新する。これは追加負荷だが、昨夜それが通話遅延を生んだ計測証拠はない。
- EchoNote音声録音を有効にしていれば追加のAudioContext/MediaRecorderが動作し、30分ごとにHTTPアップロードする。このときの上り混雑も未測定。常時自動録音ではなく、有効時のみの経路。
- LiveKitのUDP/TCP/TURNの実際の選択、接続地域、パケット損失、RTTは昨夜の値が不明。Zoomとは異なる通信経路なので、Zoomで正常だったことだけでは除外できない。Vercelはトークン発行等を担当し、通話メディアはLiveKitを通る。

## 次の調査を成立させる最小の変更案（下記1・2の診断を実装）

1. 会話音声の診断を録画・AIモードから独立して収集する。受信音声のbuffer/target/minimum delay、jitter、loss、concealed samples、ICE candidate pair RTTとprotocol/relay種別、マイク実設定、録画・AIの状態変化を時系列にする。相手側の計測も必要。RTTやbuffer値のどちらも単独では一方向の全遅延を表さない。
2. 直近数分だけ保持して、遅延発生時に匿名の診断JSONを保存できるようにする。トークン、SDP、IPアドレス、参加者名、会話内容は保存しない。
3. 同じPC・回線・参加者・物理マイク/出力で、通話のみ→カメラあり→収録レイアウト→録画→AIを順に比較し、遅延発生時の統計で切り分ける。最初から全機能を同時に変更しない。
4. 計測に基づき、100ms固定指定の撤回/調整、音声設定、録画描画負荷、通信経路を修正する。入室時の実マイク選択確認は別の明確な改善対象。

## 承認後の診断機能実装

ユーザーの「着手してください」を受け、通常通話の診断を追加した。原因確定や遅延修正完了を意味しない。音声の品質・バッファ・機器設定は変更していない。その後の「デプロイして」を受け、本変更をmain経由で本番公開する。公開結果はVercelのデプロイ状態と本番配信ファイルで別途確認する。

- `lib/call-diagnostics.ts`: 人間側のRoomごとに独立した収集器。2秒ごとの音声RTCStats、接続状態、再生許可、機器種別の変更、表示状態、AI/録音/録画/収録レイアウトの状態を記録。1秒タイマーが前面表示中に500ms超遅れた場合はスケジューリングの空白として記録するが、CPUが原因とは判定しない。
- 保持は直近最大5分・500件・音声24トラックまでのメモリのみ。退出・リロードで失われる。統計取得は1.5秒で待機打ち切り。退出や再接続前の非同期結果を破棄する。
- `components/CallDiagnosticsBar.tsx` / `components/RoomView.tsx`: 通常画面・収録画面の両方に固定高40pxの診断欄。収録ステージの外側に配置し、表示文言が変わっても高さを変えない。レイアウト変更やAI停止では収集器を作り直さない。
- 「今、遅れた」は**押した時点**を記録する。「診断を保存」でJSONをローカル保存。自動サーバー送信なし。IP、SDP、トークン、参加者名、機器名・ID、音声内容を出力しない。開始UTC時刻と相対ミリ秒を含めるが、PC間の時計ずれは別途考慮が必要。
- bufferは累積値の差分/出力数の差分から求める。未取得・初回・カウンターリセットはnull、実測ゼロと区別。無音やパケット増加なしだけでは警告しない。受信buffer>250ms、20パケット以上の区間でloss>10%は注意表示の目安であり、遅延原因の確定条件ではない。
- マイク設定はsampleRate/channelCount/echoCancellationのみ。機器ID・名前は保存しないため、物理マイク/仮想マイクの特定は画面で別途確認する。

### 次回の収録なし4名テスト

1. この変更を公開してから、通常の4名通話で再現を確認する。AI/録画は最初はOFFにする。
2. 取り残された感覚が出たら「今、遅れた」を押し、退出せず5分以内に「診断を保存」。正常な参加者側も同じタイミングで保存すると比較できる。
3. 再接続イベント、RTT/loss/bufferの変化、ブラウザ処理間隔の空白、モード切替を照合して次の修正対象を決める。RTT・bufferだけから一方向の会話遅延を断定しない。

# 設計見直し: AI参加者の音声経路を単純化する

status: レビュー依頼中（実機検証の結果を受けた再設計）

## 背景: 何が起きているか

「人間2名 + ChatGPTデスクトップ音声」の3者収録を、Windows の仮想オーディオ
デバイス経由で実装した。機能自体は一度すべて疎通したが、**設定が頻繁に壊れる**。

実機で観測した破綻の実例:

1. ChatGPT はマイク入力に「既定の**通信**デバイス」を使うが、出力は「既定の
   デバイス」を使う。音量ミキサーのアプリ別入力設定は**無視される**
2. 音量ミキサーの ChatGPT の行が音声セッション単位で増殖し（実機で4行）、
   どの行を設定すべきか判別できない。死んだセッションも残る
3. アプリ別設定を繰り返し変更すると壊れた状態になり、「リセット」でしか復旧しない
4. Windows の既定録音デバイスが Stereo Mix になっていて、AI の声を拾って
   ChatGPT へ送り返すハウリングが発生（アプリ側でガードを追加して回避）
5. Chrome がサイト別にマイクを記憶しており、Windows の既定を変えても追従しない
6. VoiceMeeter のバス（A1/B1）とデバイス名（Voicemeeter Out A1/B1）の対応が
   分かりにくく、ChatGPT が別バスを掴んでいても気づけない
7. PC 再起動・アプリ再起動のたびに上記のいずれかが変わる

## 現行設計の依存点

正常動作のために**同時に成立していなければならない条件**:

| # | 条件 | 壊れる契機 |
|---|---|---|
| 1 | 再生の既定デバイス = ヘッドホン | VoiceMeeter インストール、リセット |
| 2 | 録音の既定デバイス = 物理マイク | VB-CABLE/VoiceMeeter インストール |
| 3 | 録音の既定**通信**デバイス = Voicemeeter Out B1 | 再起動、ドライバ更新 |
| 4 | ChatGPT のアプリ別出力 = CABLE Input | ミキサーのリセット、セッション増殖 |
| 5 | VoiceMeeter が起動している | 再起動、自動起動未設定 |
| 6 | VoiceMeeter の Virtual Input が B のみ点灯 | 手作業ミス |
| 7 | VoiceMeeter のハードウェア入力が未割当 | 手作業ミス |
| 8 | Chrome のサイト別マイクが物理マイク | Chrome の記憶 |
| 9 | アプリ内の3つのデバイス選択 | localStorage 消去 |

**9箇所すべてが同時に正しい必要があり、どれか1つ崩れると無音かハウリングになる。**
しかも大半は OS 側の設定で、アプリからは検出も修正もできない。

## 選択肢

### A. 構成を1本のケーブルに落とす（ChatGPT は相手の声を聞かない）

- ChatGPT 出力 = CABLE Input（アプリ別設定 1箇所）
- ChatGPT 入力 = 物理マイク（既定のまま。**設定不要**）
- アプリは CABLE Output を読むだけ。**VoiceMeeter も入力ミキサーも不要**
- 依存点は 9 → 3 に減る

制約: ChatGPT はホストの声しか聞かない。リモート参加者の発言はホストが
口頭で要約して伝える運用。**録画・配信には3者すべての声が入る**（制約は
「ChatGPT の耳」だけ）。

### B. 現行構成のまま、壊れた箇所を検出する仕組みを足す

アプリが起動時に9条件を検査し、崩れていれば具体的に指摘する。
設定自体は変えられないので、**壊れる頻度は変わらない**。

### C. OpenAI Realtime API に差し替える

AI を WebRTC ピアとしてアプリ内に置く。**OS の音声ルーティングが完全に消える**。
依存点は 0。要件は Phase 1 で API 非依存を求めているが、§31 で将来の
OpenAIRealtimeProvider を明示しており、AiParticipantProvider 抽象は
この差し替えのために設計済み（AC-006）。

コスト: OpenAI API の従量課金。ChatGPT サブスクリプションとは別会計。

### D. VoiceMeeter をやめて VB-CABLE A+B（有料5€）にする

常駐アプリとバス概念が消える。依存点は 9 → 6 程度。
ただし Windows のデバイス役割の問題（#3, #4）は残る。

## 評価

| | 安定性 | 構築の手間 | 3者会話 | 追加費用 |
|---|---|---|---|---|
| A | 高（依存3） | 小 | ✗ ChatGPTは相手の声を聞かない | なし |
| B | 低（依存9のまま） | 中 | ○ | なし |
| C | **最高（依存0）** | 中 | ○ | API従量 |
| D | 中（依存6） | 小 | ○ | 5€ |

## 決定（2026-08-20・店主判断）

**選択肢A（ホスト媒介モード）は却下。** 「人間×人間×AI の3者が対等に会話する」ことが
この企画の最低条件であり、ホストが相手の発言を要約して AI に伝える運用では成立しない。

したがって残る選択肢は B / D / C の3つ。評価軸を「3者対等」を満たす前提で引き直す。

| | OS手動設定への依存 | 常駐アプリ | 追加費用 | 3者対等 |
|---|---|---|---|---|
| B（現行・VoiceMeeter） | 9 | 必要 | なし | ○ |
| D（VB-CABLE A+B） | 約6 | 不要 | 5€ | ○ |
| C（Realtime API） | **0** | 不要 | API従量 | ○ |

### 論点

Windows + デスクトップ ChatGPT の構成では、**第三者アプリのデバイス割り当てが
再起動のたびに変わる**ことが不安定さの根本原因で、アプリ側から制御も検出もできない。
B と D はこの構造を抱えたままなので、壊れる頻度は下げられても消せない。

C は AI をアプリ内の WebRTC ピアにするため、**OS の音声ルーティングが丸ごと消える**。
人間の声をミックスして渡す処理は既存の ChatGptInputMixer が流用でき、AI の出力トラックは
既存の Registry / publish / タイル表示へそのまま流せる。

### C を採る場合の非機能要件（レビュー指摘より）

- Realtime セッションの**60分上限**。長尺収録では時間到達時の切断・再接続・
  会話文脈の扱い・録画/publish の継続を評価する必要がある
- API キーをブラウザに置けないため、**一時トークンを発行するサーバーエンドポイント**が要る
- 従量課金。1収録あたりの費用を計測してから本採用を判断する

### 未決点（店主判断）

1. API 従量課金を許容できるか（許容できるなら C が本命）
2. 許容できない場合、D（5€でVoiceMeeterを消す）+ 収録前チェックの充実で
   運用に耐えるか。壊れる頻度は下がらないが、原因特定は数秒で済むようになる
